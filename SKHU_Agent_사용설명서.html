SKHU Agent 사용설명서

박종범 강사 · jongbum3.park@sk.com

Coding Based Education Is Almost Solved

You can teach yourself by yourself.

배경 (Motivation) & 문제 정의 (Problem)

Motivation

  • LLM 추론 비용의 급격한 감소로 셀 단위 의미 평가가 대규모로 실용화됨
  • Jupyter Notebook은 ML·데이터 과학·알고리즘 교육의 사실상 표준 형식으로 자리잡음
  • 그러나 기존 도구는 문서 전체를 검색 단위로 취급하며, 셀(cell)을 독립 검색 단위로 다루지 않음
  • 학생들은 수업 외 시간에 키워드 검색 또는 전체 재독이라는 비효율적 수단에 의존

Problem

  • 대학 코딩 강의는 지식을 .ipynb 형식으로 배포하지만, 강의 자료 누적 시 탐색 비용이 급증
  • 수업 외 시간에 특정 코드·개념을 쿼리·교차 참조할 효율적 수단이 부재
  • 키워드 검색은 코드의 의미적 맥락을 포착하지 못하고, 전체 재독은 시간 소모적
  • 비동기 학습 환경에서 강사에게 즉시 질문할 수 없어 자기주도 이해에 큰 장벽 존재

연구 질문 (Research Questions) & 목표 (Objective)

Research Questions

  • Q1. 하이브리드 검색(Vector + BM25 + Graph)이 키워드 검색 대비 코드·개념 Q&A 정확도를 향상시키는가?
  • Q2. Force Mode(전 셀 LLM 평가)가 인덱스 기반 검색보다 정밀 코드 탐색에서 더 높은 재현율을 달성하는가?
  • Q3. Agentic Mode(계획 기반 다단계 에이전트)가 복합·비교·"모두 나열" 형 질문에 단일 패스 RAG보다 더 완전한 답변을 생성하는가?

Objective

  • 하이브리드 RAG 파이프라인(Vector + BM25 + Graph RAG)으로 .ipynb 강의 자료의 셀 단위 의미 검색 지원
  • 검색 전략 단계적 확장: 일반 RAG → Force Mode → Agentic Mode (질문 복잡도에 따라 선택)
  • 자기주도 학습이 가능한 대화형 강의 보조 시스템 구축 — 강사 부재 시에도 지도 교육에 준하는 이해 달성
  • 강의 자료 변경 시 자동 재색인 및 지식 그래프·위키 자동 생성으로 지속적 학습 지원

시스템 모델 & 제약 조건

System Model

  • 입력: 쿼리 q + N개 Jupyter 노트북 코퍼스 D (각 노트북 → 셀 c₁…cₖ 분해)
  • 검색: Vector(FAISS) + BM25 + Graph RAG 병렬 수행 후 앙상블 병합 (최대 10 docs)
  • 출력: 셀 출처 S ⊆ D와 함께, 검색된 근거만으로 생성된 근거 기반 답변 a

Assumptions

  • 셀 경계가 의미 있게 구성됨 (셀당 하나의 개념 또는 코드 블록)
  • kiwipiepy 한국어 형태소 분석으로 기술 한국어 텍스트의 BM25 재현율 향상
  • FAISS 인덱스가 대상 코퍼스 크기(< 10,000 셀)에서 호스트 RAM 내 적재 가능

Success Criteria

  • 사실적 답변의 ≥ 80%에서 관련 셀 출처 인용
  • Force Mode: 상위 5개 청크 내 목표 코드 스니펫 반환
  • Agentic Mode: 3회 반복 내 모든 하위 질문 완전 커버

Constraints

  • 입력 코퍼스 .ipynb 한정 (PDF · .py · 텍스트 파일 제외)
  • 외부 LLM API 필수 (OpenAI 또는 호환 로컬 엔드포인트); 온디바이스 추론 미지원
  • 노트북 변경 시 수동 인덱스 재구축 필요 (실시간 증분 인덱싱 미지원)
  • Agentic Mode · Wiki 생성은 완성된 RAG 인덱스 선행 필요

env.txt — 필수 환경변수

API 키와 모델 설정을 한 곳에서 관리

env.txt

LLM_MODEL=gpt-4o
LLM_BASE_URL=
EMBEDDING_BASE_URL=
EMBEDDING_MODEL=text-embedding-ada-002
FORCE_WORKERS=3
키설명
OPENAI_API_KEYOpenAI API Key (필수)
LLM_MODEL답변 생성 모델
LLM_BASE_URLOpenAI는 빈값, 로컬은 http://localhost:11434/v1 등
EMBEDDING_BASE_URL / EMBEDDING_MODEL임베딩 서버·모델 (선택)
FORCE_WORKERSForce Mode 병렬 워커 초기값 (1–10)

12

📓 셀 보기 + 채팅 — 실행 예측 (LLM Emulation)

실행 없이 결과를 미리 가늠해보기

노트북을 실제로 실행하지 않고, LLM이 처음부터 끝까지 실행한다고 가정하여 각 셀의 결과를 예측합니다.

  1. 셀 보기 우측 채팅 패널 상단 ▶ 실행 예측 버튼 클릭
  2. LLM이 코드 셀을 순서대로 모의 실행 — 변수·함수·임포트 상태를 다음 셀까지 이어감
  3. 각 코드 셀마다 ### 셀 #N 실행 결과 아래 예상 출력 표시 (print, 표현식 자동 출력 등 Jupyter 컨벤션)
  4. 에러가 예상되면 Traceback 형태로 표시 + 이후 셀에 미치는 영향까지 예측
  5. 마크다운 셀은 건너뛰고 코드 셀만 대상

캐시 & 재예측

  • 노트북별로 결과 캐시 (run_predict_cache.json) — 파일 MD5 + 프롬프트 MD5로 변경 감지
  • 노트북·프롬프트 변경이 없으면 버튼 재클릭 시 LLM 재호출 없이 캐시된 예측을 즉시 표시
  • 🔄 버튼 — 캐시를 무시하고 강제로 다시 예측
실행 환경이 없거나, 실행 전 결과를 미리 가늠해 보고 싶을 때 사용합니다.

→ 다음: 17-1. 위키 Q&A — 동작 원리

17-1

🗺️ 위키 Q&A — 동작 원리 (핵심 개념)

임베딩이 아닌 키워드 매칭 방식

FAISS/BM25/Graph RAG 파이프라인을 쓰지 않고, 미리 생성된 위키 .md 페이지를 LLM 컨텍스트로 직접 넣는 경량 방식입니다.

단계내용
① 페이지 로드wiki/*.md 전체 로드 (index.md·log.md 제외)
② 키워드 매칭질문을 단어로 분해 → 각 페이지에 등장한 단어 수로 점수 (임베딩 X)
③ 상위 선택점수 상위 5개 페이지만 선택 (점수 0 제외)
④ 컨텍스트화각 페이지 앞 500자만 잘라 결합
⑤ 답변"위키 범위 내에서만 답하라" 지시로 LLM 스트리밍

잘 되는 질문: 자료의 용어를 그대로 쓴 개념·요약·비교 질문
어려운 질문: 모호·짧은 질문, 동의어/영어, 페이지 500자 이후 세부 내용

⚠️ 위키를 먼저 생성해야 하며, 글자가 겹치지 않으면 검색되지 않습니다.
의미 기반 정밀 검색은 채팅 탭(일반 RAG·/a·/f)을 사용하세요.
